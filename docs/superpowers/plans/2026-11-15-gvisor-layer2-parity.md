# gVisor Layer 2 parity map

**Goal:** move the relevant Layer 2 behavior into the GameBond userspace edge without claiming host-switch features that the gVisor edge cannot currently enforce.

**Status:** in progress. This plan covers the three repositories that participate in the live path: `Speedify` (client Ethernet adapter), `GameBond.Core` (transport and switch decisions), and `GameBond.Server` (gVisor gateway and Linux edge).

## Architecture update (2026-11-15)

Use supervised host daemons where the host owns the protocol endpoint: FRR for BGP/EVPN, hostapd/wpa_supplicant for 802.1X, and mstpd for host Linux bridges. The gVisor broker's authenticated session ports are not Linux bridge ports, so mstpd cannot control them without replacing the userspace switching path. Core owns a single-instance IEEE 802.1w RSTP state machine and bounded IEEE 802.1D version-0 BPDU compatibility, including direct BPDU transmit/receive, root and port-role election, forwarding gates, legacy timers, TCN/TCA, topology-change propagation, and per-port migration timing: an initial three-second RSTP window, legacy-mode lock, and return to RSTP after a rapid BPDU. Local timer bounds and relationships are validated for both configured bridges and received rapid/legacy BPDUs, and selected root timers are propagated. Full Clause 17 migration/management behavior, dynamic timer management, and MSTP remain incomplete. The broker exposes explicit EAPOL TAPs for hostapd; FRR EVPN uses managed kernel VXLAN devices on a Linux bridge plus a persistent broker TAP/frame pump; the static userspace VXLAN transport remains a separate non-EVPN option. EVPN-MH identity is configured on a managed CE-facing Linux LACP bond, not on the broker TAP, and remains partial pending two-PE dataplane and DF validation.

Work is grouped into four areas: (1) switching and segmentation (Q-in-Q, PVLAN, MVR, userspace RSTP); (2) edge access control (hostapd event to broker authorization over the local management socket); (3) gateway services (DHCPv4/v6 relay, IA_PD, ECMP); and (4) routed fabric (FRR EVPN and kernel VXLAN). MVR uses static group mappings; Q-in-Q, PVLAN, MVR, RSTP, and EVPN remain partial pending end-to-end/deployment validation. EVPN-MH now has managed-bond ESI/DF configuration, but remains partial until two-PE Linux dataplane and DF tests pass; local mobility groups alone do not provide MC-LAG.

### Additional enterprise-routing and timing backlog

Prioritize the newly identified gaps in this order:

1. **VRF / routing-table isolation:** decide whether the existing independent per-VLAN gVisor routers are sufficient. If not, design routing instances attachable independently of VLANs, then add route leaking and VRF-aware FRR BGP/OSPF. This is a product/design decision before implementation.
2. **MACsec:** define the Linux interface and key-management boundary, then implement and validate IEEE 802.1AE link encryption and interoperability.
3. **PTP (IEEE 1588):** decide whether Pro AV needs sub-microsecond synchronization; if so, supervise a Linux PTP service and report clock and port health, including hardware timestamping requirements.
### Lower-priority routing follow-ons

- **IS-IS:** add supervised FRR `isisd` configuration, validation, lifecycle, status, and Linux integration coverage if required.
- **RPKI route-origin validation:** define cache reachability and failure policy, then integrate FRR RTR cache and per-neighbor validation policy/status.
- **Explicit route redistribution:** define allowed OSPF/BGP/static source and destination combinations, route maps/tags, loop prevention, default handling, and validation before enabling redistribution.

## Current topology

- `Speedify/native-edge/lan` reads and writes client Ethernet frames.
- `GameBond.Core/bond` wraps Ethernet frames in the bonded transport and owns the current `L2Switch` implementation.
- `GameBond.Server/edge.Run` creates one `l2Edge` and one `L2Switch` per process/session by default. With `l2.segment_id` plus `l2.bridge`, `cmd/edge` instead attaches one authenticated session port and one shared gateway service port to a named in-process `SegmentFabric`.
- `GameBond.Server/l2gw` is a router built on one gVisor network stack. It answers gateway traffic and forwards IP flows to ordinary sockets. It is not a multi-port Ethernet bridge.
- `GameBond.Server/gateway/layer2` manages host Linux bridges and physical ports through a separate host control plane. Those controls do not automatically apply inside `l2gw`.

The opt-in path switches frames before its gateway. A broker process can serve its named fabric over an authenticated local Unix socket, allowing separate `cmd/edge` processes on the same Linux host to share FDB, VLAN and multicast state. Broker-owned per-session tokens select ingress identity and port policy. The Unix socket is same-host IPC. Cross-host frames can instead use the separate static-peer user-space VXLAN transport or the managed Linux VXLAN/bridge/TAP data path with FRR EVPN; VTEPs and session configuration are operator-managed, and the static transport does not authenticate VTEPs.

### Newly ranked enterprise operations and edge protection

Operational basics and edge protections now have partial implementations: remote syslog supports best-effort UDP and verified TLS; NTP health is read from the host while the OS owns synchronization; RA Guard is opt-in per port; and VRRP BFD tracks a distinct on-link upstream neighbor. DHCP-backed DAI/IP Source Guard covers IPv4/ARP and opt-in DHCPv6 IA_NA source checks; MAB remains unimplemented. RBAC, SNMP, flow export, and admin AAA remain management-plane gaps. Q-in-Q, PVLAN/MVR, VXLAN/EVPN, PIM, and ECMP/PBR remain partial or unsupported pending the specific end-to-end and deployment work listed above.

DHCPv6 reservations are configured inside a gateway's `hosts6` list (including each VLAN gateway's nested config). Each record requires the hex payload of the DHCPv6 Client Identifier, its IAID, the client's unicast MAC, an IPv6 address inside that gateway prefix, and a name. Example: `{"client_id_hex":"000301020304","iaid":7,"mac":"02:09:08:07:06:05","ip":"fd78:78::20","name":"console-6"}`. The DUID/IAID and MAC must all match before the reserved address is offered; active lease renewals and releases also remain tied to the authenticated session attachment that acquired them.

### Same-host segment attachment

For a same-host multi-process segment, configure one broker edge with `l2.segment_id`, `l2.segment_socket_path` (for example `/run/gamebond-segment/fabric.sock`), `l2.segment_members_file`, and `l2.bridge`. A single-network gateway also requires `l2.exit_vlan.access_vlan`; a multi-VLAN gateway uses `l2.bridge.vlans`. The broker process owns the gVisor gateway and its tunnel port. Its members file is a JSON array of records containing `identity`, `token_hex`, `vlan`, and optional port limits, `ra_guard`, `ipv4_source_guard`, `ipv6_source_guard`, `static_source_bindings`, `multicast_router`, or `mac_auth`. Each record must specify an access VLAN or trunk allow-list. Set guard fields for untrusted session access; gateway service ports remain trusted. The identity must be `session-` followed by that session's 32 lowercase hexadecimal session ID. Generate a different random token of at least 32 bytes for each session and store it as hex. A `mac_auth` member must use an access VLAN and unique `eapol_tap_name`; host PortAuth maps that TAP to the same segment identity. The switch pairs each session only with its TAP. One station is allowed per TAP/interface through `exclusive_port`. MAC authorization uses the separate broker admin token (`l2.segment_admin_token_file`) and the host gateway's local 802.1X event API; attachment tokens cannot change authorization state.

Each remote session config uses the same `segment_id` and socket path plus `segment_token_file`; it omits `bridge`. The token file contains only the hex token and must be a regular file with mode `0600` or stricter. The broker members file has the same file permission requirement. Mount the same local Docker volume (default name `gamebond-segment`, overridable with `GAMEBOND_SEGMENT_VOLUME`) at `/run/gamebond-segment` in every participating container. The broker selects VLAN membership and port limits from its authorization record; a connecting process cannot choose its VLAN or ingress identity. This socket is local-host IPC, not a cross-host transport.

For standalone PVLAN, configure `l2.tunnel_private_vlan` and `l2.exit_private_vlan` with `group_id`, `role`, and `primary_vlan`; isolated/community roles also need `secondary_vlan`, and community needs `community_id`. For a single-network gVisor gateway, set `l2.bridge.private_vlan` and the exit access VLAN; the gateway service port receives the promiscuous primary role automatically, so omit `exit_private_vlan`. For shared segments, configure `private_vlan`, `private_vlan_role`, and `private_vlan_primary_vlan` on each broker member. Isolated/community members also set `private_vlan_secondary_vlan`; community members set `private_vlan_community`. Multi-VLAN gateway roles use `l2.bridge.vlans[].gateway.private_vlan`. Each member's VLAN policy must admit only its primary or secondary VLAN as appropriate, and validation rejects ordinary ports that could bypass the mapping.

For source enforcement, set `ipv4_source_guard: true` and/or `ipv6_source_guard: true` in a broker member record. Optional `static_source_bindings` entries pin an IP/MAC pair, for example `{"ip":"192.0.2.20","mac":"02:00:00:00:00:20"}`; the access VLAN is inferred. Single-tag trunks use an explicit `vlan`, while Q-in-Q uses `outer_vlan` and `inner_vlan` (omitted only for a Q-in-Q customer access VLAN). The matching family guard must be enabled and the VLAN pair must be admitted by that member's policy. Static entries remain alongside DHCP-learned bindings and conflicting IP/VLAN-to-MAC mappings are rejected. The broker also refreshes VLAN-scoped bindings from DHCP leases carrying authenticated session identity. The switch checks IPv4 sources, ARP sender MAC/IP pairs, global IPv6 source addresses, and IPv6 Neighbor Advertisement targets against bindings before learning or forwarding. Neighbor Advertisements are parsed through the supported bounded extension-header chain; fragments and malformed chains fail closed on guarded ports. DHCP discovery and RFC 5227 ARP probes are allowed before a binding exists; IPv6 link-local sources remain available for link-local control traffic. When the gateway is configured with an IPv6 /64 and a trusted router port advertises an autonomous PIO, validated DAD creates a tentative SLAAC claim which is promoted after the DAD window; its lifetime cannot be extended by traffic and a zero-lifetime PIO withdraws it. Linux deployment and adversarial renewal/conflict validation remain outstanding.

To relay IPv4 DHCP instead of serving a local pool, set `dhcp_relay4` on each `l2.bridge` (or nested VLAN gateway), for example `"dhcp_relay4":"192.0.2.53:67"`. An off-subnet server also needs `dhcp_relay_gateway4` set to an on-link router in that gateway prefix. Do not set `dhcp_start`, `dhcp_end`, or fixed IPv4 `hosts` in relay mode. The relay sends the authenticated attachment identity in Option 82 Circuit-ID and validates the matching transaction and server before returning an OFFER/ACK/NAK to the VLAN. DHCPv6 relay is also available per gateway using `dhcp_relay6` and optional `dhcp_relay_link_address`; it validates the upstream peer, transaction, relay addresses, and Interface-ID before returning a reply to the authenticated ingress attachment. Each family currently supports one upstream server without failover.

## Implemented integration

The segment/session contract, same-host socket broker, VLAN switch before routing, per-VLAN gVisor gateways, authenticated DHCPv4/v6 lease identity and relays, IA_PD allocation with delegated-prefix routes and static router neighbors, constrained mDNS reflector, LLDP-MED policy advertisement, multicast fallback and last-member query behavior, kernel VXLAN-to-broker TAP attachment, FRR EVPN config generation, and capability states are wired. The same-host Unix-socket deployment uses the shared `segment-fabric` Docker volume; do not share that volume between hosts. Cross-host VXLAN/EVPN uses the kernel underlay path and operator-managed VTEPs, not the Unix socket volume.

Remaining gaps include Linux deployment validation for PVLAN and mixed PVLAN/MVR, DHCP relays, Q-in-Q, MVR, userspace STP, EVPN/VXLAN, CoPP load behavior, and SAVI; Linux validation of preferred-lifetime deprecation, periodic renewal, valid-lifetime and graceful-shutdown withdrawal, delegated-prefix downstream forwarding, and adversarial renewal/conflict behavior; complete Clause 17 migration/management behavior, dynamic timer management, and MSTP in gVisor; two-PE EVPN-MH/ESI dataplane, LACP, MAC synchronization, split-horizon, failover, and DF validation before claiming MC-LAG; Linux capture validation for port mirroring; SNMPv2c/v3, flow export, TACACS+ administrator AAA, PIM; NTP service configuration, MAB, host CoPP, ZTP, live BFD telemetry and Linux failover validation, and admin RBAC. Broader enterprise routing/time/security gaps remain VRF-aware routing instances, MACsec, PTP, IS-IS, RPKI origin validation, and explicit route redistribution.
